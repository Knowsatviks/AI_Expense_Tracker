AI Expense Tracker

Architecture report • React + Vite + Express + PostgreSQL + Gemini

Deep architecture documentation for the expense tracker

This project is a full-stack financial assistant that lets users register, create transactions and categories, set budgets, and receive AI-generated insights through Gemini. The system is intentionally simple, secure, and data-oriented: React on the frontend, Express on the backend, PostgreSQL for persistence, and JWT-based auth.

1. Executive Summary

The application solves a practical problem: helping users understand and control personal finances without needing a complex enterprise suite. The product is centered on four core loops: capture income and expenses, organize them with categories, enforce spending control with budgets, and get AI-generated interpretation through insights.

The architecture is intentionally modular. The frontend is a React single-page application with route-based pages and a shared auth context. The backend exposes a REST API that is protected by JWT middleware and orchestrates all database reads/writes. PostgreSQL stores all entities, while Gemini is used as a side-channel intelligence service for recommendations and summaries.

3. Frontend Architecture

React architecture

The frontend uses a route-driven React architecture with a layout shell and nested route pages. The app bootstraps through main.jsx, which wraps the app in BrowserRouter, AuthProvider, and the global toaster. The route tree is declared in App.jsx.

The design choice here is to keep the app as a single-page experience while protecting pages behind authentication and centralizing shared UI concerns. The app relies on React state for page-level data and uses Axios-based API calls for backend communication.

Routing, state management, and UI patterns
  • Routing: React Router handles public routes and protected layout nesting.
  • State management: Local React state is used per page; global auth lives in AuthContext.
  • Hooks: useState, useEffect, useMemo are used for data loading, filtering, pagination, and chart preparation.
  • Context: AuthContext exposes user, loading, login, register, logout.
  • API layer: Axios instance attached to localStorage token; handles 401 redirects to login.
  • Styling: Tailwind CSS via Vite plugin; page-level classes create a polished UI.

5. Application Execution Flow

End-to-end startup and user interaction
  1. The browser loads the Vite frontend entry point through index.html.
  2. React mounts main.jsx and renders the app inside BrowserRouter.
  3. The AuthProvider checks localStorage for a JWT token.
  4. If a token exists, it calls /auth/me and restores user state; otherwise it leaves the user unauthenticated.
  5. The router decides whether to show public auth pages or the protected layout.
  6. When the user navigates to a page, the matching route component loads and triggers its own data requests.
  7. Each page uses Axios, which attaches the JWT to the Authorization header.
  8. Requests hit Express routes, which run auth middleware where needed.
  9. Controllers query PostgreSQL through the shared connection pool.
  10. For insights and analysis, Gemini is invoked with structured prompts and the result is parsed as JSON.
  11. The frontend updates local state and re-renders the UI, often with toast notifications and charts.
Browser -> React Router -> AuthContext -> Axios -> Express Route -> Controller -> PostgreSQL -> Response -> React State -> UI

7. Authentication Flow

How auth works

Authentication is implemented with JWTs signed on the server using the jsonwebtoken package. The login and register handlers create a token using signToken(user.id) and return it to the client. The frontend stores it in localStorage and sends it as a Bearer token on subsequent calls.

Sequence 
User -> Login form -> AuthContext.login -> POST /auth/login -> authController.login -> JWT sign -> client stores token -> later /auth/me -> protect middleware -> user record returned
Security notes
  • Passwords are hashed with bcrypt before storage.
  • JWTs carry only the user identifier; the backend trusts them after signature verification.
  • The protect middleware blocks unauthorized requests with 401.
  • The frontend removes the token and redirects to login on 401.

8. Database

Database choice and design principles

The project uses PostgreSQL, not MongoDB. The schema is relational and intentionally normalized around users, categories, transactions, budgets, and AI insight records. It favors explicit foreign keys and data integrity constraints over document flexibility.

Schema overview
TablePurposeKey relationships
usersStores authentication and profile data.Parent for categories, transactions, budgets, ai_insights.
categoriesStores transaction categories and tags.Belongs to a user; linked by transactions and budgets.
transactionsRepresents financial events.Belongs to a user and optionally a category.
budgetsRepresents spending limits per category.Belongs to user + category.
ai_insightsStores generated AI analysis output.Belongs to a user.
Table-by-table field notes
  • users: id, name, email, password_hash, currency, created_at.
  • categories: id, user_id, name, type, icon, color, is_default, created_at.
  • transactions: id, user_id, category_id, amount, type, description, notes, transaction_date, created_at.
  • budgets: id, user_id, category_id, amount, period, start_date, created_at.
  • ai_insights: id, user_id, insight_type, period_start, period_end, content_json, created_at.
Important queries and CRUD behavior
  • Registration inserts into users and then seeds categories for the new user.
  • Login selects users by email and compares the incoming password to password_hash.
  • Transactions are filtered by user, date, category, type, and search string.
  • Budgets are joined with categories and transactions to calculate spent values.
  • Dashboard summary aggregates monthly income and expenses with windowed SQL.
  • Insights are stored as JSON in ai_insights.content_json.
-- Example: get recent transactions with category details
SELECT t.*, c.name AS category_name
FROM transactions t
LEFT JOIN categories c ON t.category_id = c.id
WHERE t.user_id = $1
ORDER BY t.transaction_date DESC, t.id DESC;

The integration lives in backend/utils/gemini.js. It creates a GoogleGenAI instance from the GEMINI_API_KEY environment variable. The app uses the Gemini 2.5 Flash model.

13. Middleware

Auth middleware

The project has one core middleware: protect. It reads the Authorization header, expects a Bearer token, verifies it with the JWT secret, and injects req.userId into the request when valid. 

export const protect = (req, res, next) => {
  const authHeader = req.headers.authorization;
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ message: 'Not authorized, no token' });
  }
  const token = authHeader.split(' ')[1];
  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.userId = decoded.userId;
    next();
  } catch {
    return res.status(401).json({ message: 'Not authorized, token failed' });
  }
};

17. Error Handling

  • Frontend: forms show toast notifications using react-hot-toast and surface backend error messages.
  • Backend: controllers catch errors, log them, and return structured JSON error responses.
  • Database: duplicate key errors are handled explicitly in category and budget creation.
  • Gemini: AI failures are wrapped in user-facing errors and returned as failed insight operations.

18. Security Analysis + 19. Performance Analysis

Security analysis
  • JWT-based auth protects backend routes.
  • Passwords are hashed using bcrypt.
  • Each resource query is scoped to the current user.
  • Users cannot access other users’ data because every query uses req.userId.
Performance analysis
  • The frontend loads data with parallel requests where appropriate, such as the dashboard.
  • Transactions use the browser-side useMemo to reduce re-computation of filtered arrays.
  • Charts render from pre-shaped arrays, which is ideal for Recharts.
  • Some opportunities remain: adding server-side pagination, request caching, and query optimization would help as the dataset grows.

23. Interview Preparation

Possible questions and ideal answers
  • Why use PostgreSQL here? Because the data is relational and benefits from explicit schema constraints, joins, and reporting.
  • Why is auth implemented with JWTs? To keep the backend stateless and support simple API-based client interactions.
  • Why store insight results in a table? To provide history, persistence, and consistent rendering of past AI analyses.
  • How would you scale this app? By adding server-side pagination, caching, index tuning, and possibly a queue for AI generation.
